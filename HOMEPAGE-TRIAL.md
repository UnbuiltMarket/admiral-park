# Admiral Park homepage motion trial

Paste the entire generated `src/framer/AdmiralHomepageTrial.tsx` into the existing Framer hero code file. Keeping that code file retains the existing component instance and the named `OpeningContent`, `BuildingContent`, and `ArrivalCTA` overrides. Those names are preserved; the file also exports `BalatonfuredContent`, `AranyhidContent`, and `OrbitView1` through `OrbitView8` for the native content journey. A new Code Component file is also supported, but native wrappers must then use overrides from that same new file.

Use one component filling one Relative Frame with height 100vh. The navbar stays above it as native Framer content. No sticky spacer or page content below the viewer is needed. Keep GitHub assets enabled, save, and test in Preview. Publish in Framer after accepting the trial. The editor canvas is a static still; interaction runs in Preview and on the published page.

For the quickest check, choose **Start trial: Orbit directly**. For the connected experience, choose **Full journey**. Editor view selects only the still used while editing; its SEQ_02 midway option shows the middle SEQ_02 image (frame 36).

**Orbit start frame** selects the exact first orbit image, using the filename numbers 0–119. The default is **45**, the fourth camera with eight viewpoints (0, 15, 30, 45, 60, 75, 90, 105). It applies to the editor orbit still, direct orbit entry, the normal approach-to-orbit handoff, retry and returning to the orbit after Overview. Downloads and the decode window are prioritised around the selected frame. A custom frame such as 42 stays parked exactly at 42, with the status Custom view; the first forward/backward gesture moves to the existing checkpoint at 45/30. The eight checkpoint cameras and future mask alignment remain fixed. SEQ_02 ends at frame 45, so keep the default for a matching connected camera handoff; changing the start frame to another view can introduce a visible jump at that handoff. Pausing and resuming a custom parked entry does not start movement. Values are rounded and clamped to the sequence; nonfinite values use frame 45.

The full journey is now **opening panorama → SEQ_01 → building → SEQ_02 → orbit**. SEQ_01 is the existing 65-image approach. Its 0.8-second opening and final fades are unchanged. After it reaches the building, a fresh downward gesture or Explore building starts SEQ_02. Input left over from the first approach gesture does not accidentally start the next segment. The opening panorama and building text overrides belong to SEQ_01. When SEQ_02 starts, BuildingContent and ArrivalCTA fade away over 0.5 seconds, with the existing text rise, while the camera starts its opening dissolve. Their interaction is disabled immediately, and they stay hidden after the fade. Repeated loading/frame updates do not restart it; returning to the building or Overview cancels a pending fade. Reduced-motion visitors hide the departing overlays immediately. Orbit directly bypasses both connecting segments.

SEQ_02 uses all 73 new 1920x1010 AVIF images (`02 sequence00 copy.avif` through `02 sequence72 copy.avif`) from `assets/images/SEQ_02_V01`, totalling 3,687,134 bytes (3.69 MB). Its opening image matches the SEQ_01 building view and its final image matches orbit frame 45, the default fourth camera. It uses the same scroll-triggered, continuous playback engine as SEQ_01: scroll can influence its speed and reverse it, but releasing input lets it continue toward an endpoint rather than parking between images. **SEQ_02 duration** controls its base travel time independently, defaulting to 2.5 seconds; Flight boost, Flight coast and Scroll trigger are shared with SEQ_01. Playback prepends the existing SEQ_01 end image to the 73 connection images, giving 74 logical frames with only 73 new files to download. This lets the 0.8-second opening fade cross from the exact building still into SEQ_02 without a sudden colour change; its final fade is also 0.8 seconds. Reversing back to its opening returns to the building, ready for another fresh downward gesture. Overview returns to the opening panorama.

After SEQ_02 arrives, the orbit prepares its matching parked view and takes over with the existing 0.35-second dissolve. That short dissolve remains useful for colour differences between the two renders; the lower image stays opaque to avoid a dark dip. It is separate from each camera sequence's endpoint fades. A direction change after the orbit activates rotates around the building rather than reversing SEQ_02.

Compressed SEQ_02 files are prefetched once SEQ_01 starts moving, so reading the opening view does not immediately require the complete connecting download. Decoded SEQ_02 images are created only while its player is active, using the same bounded cache as SEQ_01: 14 frames on desktop and 10 on phones. Its player releases decoded frames before orbit activation; all 73 decoded full-size images are not kept in memory together. If a connection image fails, Retry connection resumes from the current place and replaces failed image data with a fresh download. Recovery controls remain available when Trial controls is off. The downloaded compressed files remain reusable, and a late prefetch completion cannot reactivate a disposed player.

The orbit uses all 120 rerendered 1920x1010 AVIF files (`adjusted sequence0000 copy.avif` through `adjusted sequence0119 copy.avif`) from `assets/ORBIT PICKER/BEAUTY sequence_Desktop`. Total encoded size: 7,508,206 bytes (7.51 MB). They are downloaded and decoded with at most four fetches and two motion decodes at once. The default movement decode is 960px wide on desktop and 640px on phones. This reduces working memory; it does not reduce the 7.51 MB download. No source images are resampled or recompressed on disk. A separate phone control prevents an old hero component's 1280px setting from silently carrying into the orbit cache.

The encoded files remain downloaded, while decoded movement images use a bounded window. With the default eight viewpoints, Desktop buffer = 2 prepares 61 frames (two checkpoints in each direction) at 960px, approximately 118.3 MB of RGBA pixels. Phone buffer = 1 prepares 31 frames at 640px, approximately 26.7 MB. A single parked view adds up to 7.76 MB of 1920px pixels on desktop or about 3.45 MB at 1280px on phones. Encoded files, temporary decoder work, canvases and browser/GPU overhead are additional. Evicted image bitmaps are explicitly closed. The nearest checkpoint in both directions has priority during initial preparation; all 120 compressed files and that first ring must be ready for activation, then the desktop second ring fills in the background. Changing the number of viewpoints changes the frame count per checkpoint and therefore the cache size.

The complete selected route is prepared before any camera movement starts. While waiting, the current sharp still stays visible and input remains locked to the accepted command. Motion starts its full Settle time only after all required frames are resident. Adjacent navigation shifts the window toward its destination and prepares the following views in the background. A nonadjacent numbered-view jump uses its full shortest route instead of combining that route with another window. With eight viewpoints, this can temporarily use up to 61 motion frames on phones; the cache returns to the configured window after arrival. A paused route keeps its required frames pinned, and late decode completions outside the current window are closed. Downloading a file once is independent of decoding it again when revisiting an evicted view.

Moving frames are crisp by default. Frame blend crossfades the two neighbouring resident orbit images; 0% disables blending, and 100% blends across each complete frame interval. The route pins both images needed by each blend. Checkpoints always resolve to one exact sharp image, with its detail upgrade revealed over 0.12 seconds. The SEQ_01 and SEQ_02 endpoint fades and 0.35-second orbit handoff remain separate. Destroying each camera-sequence player when it is no longer needed frees its decoded frames. Hidden Framer breakpoint instances do not prepare duplicate orbit sets; hiding a previously active instance releases its bitmaps.

The October 19 rerender changes the orbit payload from 4.03 MB to 7.51 MB. SEQ_01 adds 3,521,953 bytes and SEQ_02 adds 3,687,134 bytes, for 14,717,293 bytes (14.72 MB) of encoded camera images in the full journey before Framer and other page assets. The direct-orbit trial does not need the two approach sequences. Since all source dimensions remain 1920x1010, the rerender does not increase decoded pixel memory at a fixed decode width. A local desktop Chrome benchmark measured the new 120-frame set at 960px with two concurrent decodes in 1.61 seconds (per-frame median 27.2ms, p95 34.8ms), and at 640px in 1.24 seconds (median 20.5ms, p95 25.6ms). Downloads were completed before timing, high-quality resizing was included, and every bitmap was closed after measurement. These figures describe this desktop, not a physical phone or a real network.

A wheel gesture, directional drag/swipe, or arrow triggers one complete move to the next or previous checkpoint. The input strength and scrolling speed do not affect camera speed. Each move uses Settle time, with a symmetric slow start, quicker middle and slow arrival. New orbit commands during a move are ignored rather than queued, so reversing is possible after arrival. A continuous wheel gesture is latched until a 180ms quiet gap, including across arrival, preventing trackpad momentum from starting another move; a held drag/swipe triggers only once. Repeated fresh gestures can make full revolutions. Escape or the trial Pause control can still pause accessibly; resuming continues the original transition from its remaining time. Checkpoints default to frames 0,15,30,45,60,75,90,105. Previous/Next view, numbered view buttons, Pause rotation, and Overview are trial controls. Overview returns to the opening panorama; upward orbit input rotates backward rather than leaving the orbit.

The `Settle time` control now ranges from 0.15 to 10 seconds, defaulting to 1.5 seconds. Existing Framer instances may retain their old value, so set it explicitly after pasting the update. The obsolete Wheel speed, Drag speed and Orbit coast controls are removed. `Desktop buffer` and `Phone buffer` control how many checkpoints are prepared in each direction (defaults 2 and 1, configurable 1–3). `Frame blend`, `Orbit decode`, `Phone decode`, `Stopped detail`, and `Viewpoints` allow further tuning in Framer. View arrows and numbered buttons are disabled while a transition is running. Diagnostics separate downloaded files, resident buffered movement images, required route readiness and total decoded images including the sharp still. A Retry orbit button is available for an active orbit decode failure, including when trial controls are hidden; valid compressed files are retained. Input is routed by the visible viewer's bounds, so full-size transparent Framer wrappers above the component do not swallow wheel or drag input. Covered trial buttons receive their click/tap through the same wrapper, without moving or restyling native Framer layers. Single-finger horizontal and vertical gestures rotate while the orbit is active; two-finger pinch gestures retain browser handling. This routing prevents scrolling past the viewer even if an older tall page section remains. Native navigation, form fields and genuine nested scroll panels retain their behavior; the page's own scrollbar is not treated as a nested panel. Mark other interactive overlays with `data-orbit-ignore` if needed. Arrow keys, PageDown/PageUp and Space/Shift+Space change viewpoints when the visible orbit is active, including when the page body has focus. Holding a key does not chain checkpoint moves. Escape pauses. Reduced-motion visitors use viewpoint jumps rather than animated camera travel. Hiding the tab pauses movement. All capture listeners are removed when the viewer unmounts.

## Native content journey

The native Framer content now follows **Balatonfüred → Aranyhíd sétány → eight building views**. Use `BalatonfuredContent` on the opening composition, `AranyhidContent` at the end of SEQ_01, and `OrbitView1` through `OrbitView8` on eight native sibling groups above the camera component. Legacy overrides still work. The Aranyhíd group retains its 0.5-second departure fade when SEQ_02 starts; no extra story stage is added during SEQ_02.

Keep Viewpoints at eight. The checkpoint groups map to frames 0, 15, 30, 45, 60, 75, 90 and 105; frame 45 enters at View 4. A story appears only at its exact parked checkpoint, after a default 0.12-second delay, with a 0.6-second entrance and a 0.3-second departure. Each view has its own entrance edge, exit edge and movement distance (24px by default). The native groups keep their Framer positioning; no background panel or copy is generated. Editor orbit view previews a selected camera and composition without changing the live orbit entry. See [USER-JOURNEY.md](USER-JOURNEY.md) for the layer structure, controls, direction choices and mobile layout guidance.

The apartment details strip is a design preview for the future picker. **Apartment details → Sample** shows editable example values at the bottom of a parked orbit or its editor still; the MINTA/SAMPLE label identifies that these are not project apartment records. The thin white rule and typography have no background panel, gradient, blur or shadow, so the orbit remains visible. Apartment number, area, terrace, garden, rooms, availability and a floorplan thumbnail share one horizontal row on desktop. Narrow components use a compact header and a second horizontal statistics row. The strip does not capture pointer, wheel or touch input. It fades out during camera movement; trial controls sit above its measured height when both are visible.

**Sample apartment** in the Framer sidebar edits the example apartment and optionally accepts a real floorplan image. Until supplied, the small floorplan graphic is an illustrative placeholder. Zero terrace/garden values use an em dash; missing fields do the same. **Details language** chooses Hungarian or English. **Details bottom** and **Details margin** adjust placement. **Apartment details → Off** hides the strip; **Hover** waits for actual apartment data and shows no sample record.

The future mask can send the currently hovered apartment synchronously to the visible component root; leaving an apartment sends null. The mask images, coordinate picking and apartment JSON fetching are not implemented by this design trial. A later asynchronous mask/data loader must verify its checkpoint generation before dispatching. The bridge accepts data only while the visible runtime orbit is parked at a real checkpoint; movement, leaving the viewer and Overview clear it.

```js
const root = document.querySelector('[data-admiral-homepage]')
root.dispatchEvent(new CustomEvent('admiral:apartment-hover', {
  detail: {
    id: 'A.204', number: 'A.204', area: 66.4, terrace: 12.8,
    garden: 0, rooms: 3, availability: 'available',
    floorplanUrl: 'https://example.com/floorplans/A-204.webp'
  }
}))
// Clear the hovered apartment:
root.dispatchEvent(new CustomEvent('admiral:apartment-hover', { detail: null }))
```

To connect a future native navbar Overview control, dispatch `new Event("admiral:overview")` on `window` from its click handler. This page-scoped event only acts on visible instances. The existing navbar's ordinary links need no code changes.

This trial includes camera movement, viewpoint controls and the apartment-details visual preview. Apartment masks, illuminated hover images and hover-linked apartment JSON are not connected yet. Shared apartment-type plans are available under assets/apartment-list; the sample apartment is not mapped to a verified project unit. The details preview uses clearly labelled sample values and an illustrative thumbnail; it does not simulate facade picking. It uses the full-size rerendered orbit files and the new SEQ_02 connection; lower-resolution network variants can be added after evaluating the motion.
