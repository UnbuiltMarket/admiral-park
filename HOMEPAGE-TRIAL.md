# Admiral Park homepage motion trial

Paste the entire generated `src/framer/AdmiralHomepageTrial.tsx` into the existing Framer hero code file. Keeping that code file retains the existing component instance and the named `OpeningContent`, `BuildingContent`, and `ArrivalCTA` overrides. The trial exports those same names. A new Code Component file is also supported, but native wrappers must then use overrides from that same new file.

Use one component filling one Relative Frame with height 100vh. The navbar stays above it as native Framer content. No sticky spacer or page content below the viewer is needed. Keep GitHub assets enabled, save, and test in Preview. Publish in Framer after accepting the trial. The editor canvas is a static still; interaction runs in Preview and on the published page.

For the quickest check, choose **Start trial: Orbit directly**. For the connected experience, choose **Full journey**. Editor view selects only the still used while editing.

**Orbit start frame** selects the exact first orbit image, using the filename numbers 0–119. The default is **45**, the fourth camera with eight viewpoints (0, 15, 30, 45, 60, 75, 90, 105). It applies to the editor orbit still, direct orbit entry, the normal approach-to-orbit handoff, retry and returning to the orbit after Overview. Downloads and the decode window are prioritised around the selected frame. A custom frame such as 42 stays parked exactly at 42, with the status Custom view; the first forward/backward gesture moves to the existing checkpoint at 45/30. The eight checkpoint cameras and future mask alignment remain fixed. Pausing and resuming a custom parked entry does not start movement. Values are rounded and clamped to the sequence; nonfinite values use frame 45.

The full journey uses the existing 65-image approach with 0.8-second opening and final fades. A fresh downward gesture after the building appears, or Explore building, enters the orbit. There is no connecting camera sequence in the provided folder, so this trial uses an ordinary 0.35-second handoff dissolve; the lower image stays opaque to avoid a dark dip. Repeated input from the approach's last gesture does not accidentally enter the orbit.

The orbit uses all 120 rerendered 1920x1010 AVIF files (`adjusted sequence0000 copy.avif` through `adjusted sequence0119 copy.avif`) from `assets/ORBIT PICKER/BEAUTY sequence_Desktop`. Total encoded size: 7,508,206 bytes (7.51 MB). They are downloaded and decoded with at most four fetches and two motion decodes at once. The default movement decode is 960px wide on desktop and 640px on phones. This reduces working memory; it does not reduce the 7.51 MB download. No source images are resampled or recompressed on disk. A separate phone control prevents an old hero component's 1280px setting from silently carrying into the orbit cache.

The encoded files remain downloaded, while decoded movement images use a bounded window. With the default eight viewpoints, Desktop buffer = 2 prepares 61 frames (two checkpoints in each direction) at 960px, approximately 118.3 MB of RGBA pixels. Phone buffer = 1 prepares 31 frames at 640px, approximately 26.7 MB. A single parked view adds up to 7.76 MB of 1920px pixels on desktop or about 3.45 MB at 1280px on phones. Encoded files, temporary decoder work, canvases and browser/GPU overhead are additional. Evicted image bitmaps are explicitly closed. The nearest checkpoint in both directions has priority during initial preparation; all 120 compressed files and that first ring must be ready for activation, then the desktop second ring fills in the background. Changing the number of viewpoints changes the frame count per checkpoint and therefore the cache size.

The complete selected route is prepared before any camera movement starts. While waiting, the current sharp still stays visible and input remains locked to the accepted command. Motion starts its full Settle time only after all required frames are resident. Adjacent navigation shifts the window toward its destination and prepares the following views in the background. A nonadjacent numbered-view jump uses its full shortest route instead of combining that route with another window. With eight viewpoints, this can temporarily use up to 61 motion frames on phones; the cache returns to the configured window after arrival. A paused route keeps its required frames pinned, and late decode completions outside the current window are closed. Downloading a file once is independent of decoding it again when revisiting an evicted view.

Moving frames are crisp by default. Frame blend crossfades the two neighbouring resident orbit images; 0% disables blending, and 100% blends across each complete frame interval. The route pins both images needed by each blend. Checkpoints always resolve to one exact sharp image, with its detail upgrade revealed over 0.12 seconds. The approach endpoint fades and 0.35-second handoff remain separate. Destroying the approach on orbit entry frees its decoded frames. Hidden Framer breakpoint instances do not prepare duplicate orbit sets; hiding a previously active instance releases its bitmaps.

The October 19 rerender changes the orbit payload from 4.03 MB to 7.51 MB; the approach adds 3,521,953 bytes, for 11,030,159 bytes of encoded camera images in total before Framer and other page assets. Since all source dimensions remain 1920x1010, the rerender does not increase decoded pixel memory at a fixed decode width. A local desktop Chrome benchmark measured the new 120-frame set at 960px with two concurrent decodes in 1.61 seconds (per-frame median 27.2ms, p95 34.8ms), and at 640px in 1.24 seconds (median 20.5ms, p95 25.6ms). Downloads were completed before timing, high-quality resizing was included, and every bitmap was closed after measurement. These figures describe this desktop, not a physical phone or a real network.

A wheel gesture, directional drag/swipe, or arrow triggers one complete move to the next or previous checkpoint. The input strength and scrolling speed do not affect camera speed. Each move uses Settle time, with a symmetric slow start, quicker middle and slow arrival. New orbit commands during a move are ignored rather than queued, so reversing is possible after arrival. A continuous wheel gesture is latched until a 180ms quiet gap, including across arrival, preventing trackpad momentum from starting another move; a held drag/swipe triggers only once. Repeated fresh gestures can make full revolutions. Escape or the trial Pause control can still pause accessibly; resuming continues the original transition from its remaining time. Checkpoints default to frames 0,15,30,45,60,75,90,105. Previous/Next view, numbered view buttons, Pause rotation, and Overview are trial controls. Overview returns to the opening panorama; upward orbit input rotates backward rather than leaving the orbit.

The `Settle time` control now ranges from 0.15 to 10 seconds, defaulting to 1.5 seconds. Existing Framer instances may retain their old value, so set it explicitly after pasting the update. The obsolete Wheel speed, Drag speed and Orbit coast controls are removed. `Desktop buffer` and `Phone buffer` control how many checkpoints are prepared in each direction (defaults 2 and 1, configurable 1–3). `Frame blend`, `Orbit decode`, `Phone decode`, `Stopped detail`, and `Viewpoints` allow further tuning in Framer. View arrows and numbered buttons are disabled while a transition is running. Diagnostics separate downloaded files, resident buffered movement images, required route readiness and total decoded images including the sharp still. A Retry orbit button is available for an active orbit decode failure, including when trial controls are hidden; valid compressed files are retained. Input is routed by the visible viewer's bounds, so full-size transparent Framer wrappers above the component do not swallow wheel or drag input. Covered trial buttons receive their click/tap through the same wrapper, without moving or restyling native Framer layers. Single-finger horizontal and vertical gestures rotate while the orbit is active; two-finger pinch gestures retain browser handling. This routing prevents scrolling past the viewer even if an older tall page section remains. Native navigation, form fields and genuine nested scroll panels retain their behavior; the page's own scrollbar is not treated as a nested panel. Mark other interactive overlays with `data-orbit-ignore` if needed. Arrow keys, PageDown/PageUp and Space/Shift+Space change viewpoints when the visible orbit is active, including when the page body has focus. Holding a key does not chain checkpoint moves. Escape pauses. Reduced-motion visitors use viewpoint jumps rather than animated camera travel. Hiding the tab pauses movement. All capture listeners are removed when the viewer unmounts.

The apartment details strip is a design preview for the future picker. **Apartment details → Sample** shows editable example values at the bottom of a parked orbit or its editor still; the MINTA/SAMPLE label identifies that these are not project apartment records. The thin white rule and typography have no background panel, gradient, blur or shadow, so the orbit remains visible. Apartment number, area, terrace, garden, rooms, availability and a floorplan thumbnail share one horizontal row on desktop. Narrow components use a compact header and a second horizontal statistics row. The strip does not capture pointer, wheel or touch input. It fades out during camera movement; trial controls sit above its measured height when both are visible.

**Sample apartment** in the Framer sidebar edits the example apartment and optionally accepts a real floorplan image. Until supplied, the small floorplan graphic is an illustrative placeholder. Zero terrace/garden values use an em dash; missing fields do the same. **Details language** chooses Hungarian or English. **Details bottom** and **Details margin** adjust placement. **Apartment details → Off** hides the strip; **Hover** waits for actual apartment data and shows no sample record.

The future mask can send the currently hovered apartment synchronously to the visible component root; leaving an apartment sends null. The mask images, coordinate picking and apartment JSON fetching are not implemented by this design trial. A later asynchronous mask/data loader must verify its checkpoint generation before dispatching. The bridge accepts data only while the visible runtime orbit is parked at a real checkpoint; movement, leaving the viewer and Overview clear it.

```js
const root = document.querySelector('[data-admiral-homepage]')
root.dispatchEvent(new CustomEvent('admiral:apartment-hover', {
  detail: {
    id: 'A.204', number: 'A.204', area: 66.4, terrace: 12.8,
    garden: 0, rooms: 3, availability: 'available',
    floorplanUrl: 'https://example.com/floorplans/A-204.webp'
  }
}))
// Clear the hovered apartment:
root.dispatchEvent(new CustomEvent('admiral:apartment-hover', { detail: null }))
```

To connect a future native navbar Overview control, dispatch `new Event("admiral:overview")` on `window` from its click handler. This page-scoped event only acts on visible instances. The existing navbar's ordinary links need no code changes.

This trial includes camera movement, viewpoint controls and the apartment-details visual preview. Apartment masks, illuminated hover images and hover-linked apartment JSON are not connected yet. Shared apartment-type plans are available under assets/apartment-list; the sample apartment is not mapped to a verified project unit. The details preview uses clearly labelled sample values and an illustrative thumbnail; it does not simulate facade picking. It uses the full-size rerendered orbit files; lower-resolution network variants and the connecting sequence can be added after evaluating the motion.
